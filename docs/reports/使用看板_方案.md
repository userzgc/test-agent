# 使用看板方案（未启动，待内网机器到位）

> 状态：方案已定稿，**未实施**。前置条件：一台常开内网机器（跑采集服务 + 看板）。
> 结论：看板**不依赖服务器化路径 A/B 决策**——采集协议先定，事件从 IDE 发还是从服务器发，采集端换、服务端不换。
> 操作人：userzgc ｜ 定稿日期：2026-08-26

## 1. 要解决什么

当前使用记录是本机 `docs/usage-log.csv`（SessionStart hook 追加，进 git）。已知缺陷：

| 缺陷 | 根因 |
|---|---|
| 团队看不见 | 日志在各人本机，依赖手动 git 提交，节奏与正式产出不同步，必然烂尾 |
| 多人冲突 | 多人追加同一 csv，谁后 push 谁解冲突，烦几次就没人提交了 |
| 维度单一 | 只有 时间/人/会话ID，没有用途、失败率、委派率、产出量 |

## 2. 架构（三层，采集协议与运行位置解耦）

```
[每人 IDE 的 hooks] ──POST──▶ [内网采集服务] ──▶ [SQLite/PG] ──▶ [看板]
[服务器化后的 CLI] ──POST──▶  （同一个 collector，不用改）
```

两个关键依据（均已查 `references/qoder-docs/` 证实）：

1. Qoder hooks 支持 `command` 类型脚本，脚本里 `curl` POST 即可外发事件（IDE 阶段可用）。
2. `.qoder/settings.json` 是项目级配置随 git 共享——hook 配一次，同事 pull 后自动生效，无需挨个装。

## 3. 统计维度 → 数据源矩阵

| 看板维度 | 数据源 | 采集方式 |
|---|---|---|
| 谁在用、频次、活跃时段 | `SessionStart` 事件 | hook 脚本带 `git config user.name` |
| 用途分布（qa-flow / 写用例 / 取数…） | `UserPromptSubmit` 的 `prompt` 字段 | 只截前 60 字（脱敏红线） |
| 工具失败率、失败类型 | `PostToolUseFailure` | 带 tool_name |
| 委派使用率（analyst / reviewer） | `SubagentStart` / `SubagentStop` | 带 agent_type |
| 会话轮次、时长 | `Stop` 计数；`SessionEnd` − `SessionStart` | session_id 关联 |
| 产出统计（XMind 数、台账更新、评审打回轮次） | git log + 仓库文件扫描 | collector 侧定时任务，不走 hook |
| 用例执行、缺陷（可选二期） | 禅道 | 复用 `scripts/zentao_login.py` 链路 |

## 4. 技术选型

| 组件 | 选型 | 理由 |
|---|---|---|
| 采集服务 | FastAPI + SQLite（单文件） | 收 JSON 落库，百行以内；量级远够 |
| hook 侧 | `command` 脚本组装 payload + `curl --max-time 2`，`async: true` | 纯 `http` 类型塞不进 git user.name；async 保证 collector 挂了不影响任何人干活 |
| 看板 | Metabase（备选 Grafana）直连库 | 拖拽出全部图表，零前端开发；此数据量级自研前端是浪费 |

## 5. 红线

- prompt **只截前 60 字入库**——全文可能含凭据讨论。
- 服务只部内网，不暴露公网。
- collector 不可用时 hook 静默失败（`--max-time 2` + `async`），**绝不阻塞会话**。
