# 失败处置协议

## 判定标准

工具调用返回结果**不符合预期**即视为失败，包括：
报错、401/403、超时、连接失败、Unauthorized、**空数据**、**格式不对**。

不是只有抛异常才算失败 —— 返回了但内容是空的、格式错的，同样算。

## 处置顺序（不可跳过、不可重排）

```
工具调用失败
  │
  ├─ 1. 当场记录踩坑（不等会话结束、不等用户提醒）
  ├─ 2. 分析根因
  ├─ 3. 用 AskUserQuestion 推送选项：记录踩坑 / 更新资产 / 换方案 / 继续推进
  └─ 4. 用户确认后才继续推进
```

## 禁止

- ❌ 工具失败后直接换方案继续，不记录
- ❌ 失败后转而给方法论建议，绕开问题本身
- ❌ 一次会话累积多个坑后才批量记录
- ❌ 等用户质问「为什么没记录」才补记
- ❌ 把「记录踩坑」当作可选步骤

## 记录位置：优先用 Qoder 记忆，而不是手写文件

⚠️ 历史做法是追加到 `docs/lessons-learned.md`。
但该文件**没有任何机制保证它会被加载** —— 放在 `docs/` 下等于写了没人读，
这本身就是本项目最大的一个坑。

现在的正确落点，按优先级：

| 情况 | 落点 |
|---|---|
| 可复用的教训、平台/工具的固有坑 | **Qoder 长期记忆**（`UpdateMemory`，category 选 `common_pitfalls_experience`） |
| 需要每次都生效的硬约束 | **`AGENTS.md`** 或 `.qoder/rules/` |
| 项目特有的业务口径 | `.qoder/rules/` 对应专题 |
| 需要人类翻阅的历史台账 | `docs/lessons-learned.md`（保留，但**不作为唯一落点**） |

CLI 侧可跑 `/remember` 定期评审自动积累的记忆条目并提出晋升建议。

## 手写记录格式（写 `docs/lessons-learned.md` 时）

按时间倒序，最新在上：

```markdown
## YYYY-MM-DD 场景简述
- **问题**：具体发生了什么
- **根因**：为什么发生
- **解决方案**：怎么解决的
- **关联文件**：涉及的路径
- **资产更新**：更新了哪些 rules / skills / agents / scripts（无则填"无"）
```

## 必须记录的场景

- 需求分析遗漏关键点，被用户纠正
- 用例评审发现覆盖盲区
- 脚本/工具执行失败（401/超时/连接失败）
- 工具调用方式与文档不一致
- 业务规则理解偏差
- 流程中某环节反复出错
- 能力缺失，需补充脚本或工具
- **跳过错误继续推进 → 回头补记**

## 不需要记录

- 简单语法错误（已修复且非系统性）
- 与项目无关的临时性问题
- 已有记录的重复问题

## 记录后的资产更新检查

按顺序检查是否需要更新：

1. `.qoder/rules/` 对应专题规格
2. `AGENTS.md`（仅当是每次都必须生效的硬约束）
3. Qoder 长期记忆
4. `scripts/` 工具脚本（脚本仍可用）
5. Hooks（**唯一能真正强制的机制**）

原则：
- **小步迭代** —— 只改与当前问题直接相关的，不扩大范围
- **就地更新** —— 直接改现有文件，不创建新版本文件
- **验证可用** —— 新增脚本必须自测后再被引用
- ❌ 不要在没有明确根因时盲目改规则
- ❌ 不要为了「完善」添加未经验证的内容

## ⚠️ 这条规则自身的效力边界

本文件是**上下文，不是强制策略**。
「失败必须当场记录」这类要求，只有配 `PostToolUse` hook 才真正拦得住。
目前**尚未配置**，属于已知缺口 —— 见 `AGENTS.md` 结尾。

配 hook 时注意三个易漏点（详见 `.qoder/rules/qoder-platform.md`）：
脚本要从 **stdin 读 JSON**、要 `chmod +x`、Powerlevel10k 可能污染输出。
