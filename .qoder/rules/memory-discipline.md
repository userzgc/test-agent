# 记忆纪律

原 `.trae/skills/memory-keeping/SKILL.md` 的方法论保留，**落点改为 Qoder 原生记忆 + git 内共享资产**。

## 一票判据（先问这两个问题）

1. **另一个人也会需要这条信息吗？** 会 → 必须落 git 内资产（rules / 台账 / 需求分析文档），
   个人记忆最多做副本。Qoder 记忆是**本机文件，不随 git 同步**，只存记忆 = 团队看不见。
2. **这条信息跨需求可复用吗？** 单需求的业务口径（功能口径、做不做、需求缺什么）**不落记忆**——
   它们会过期，且有天然归属地（XMind 节点标注 + 需求分析文档 + 台账）；落记忆是冗余副本，过期后反向误导。
   真正值得记的是**工程经验**：agent 跑不通后的降级处理、工具静默失败模式、环境脚本坑——不记就真丢了。

## 为什么换落点

原方案把记忆写进 `docs/memory/decisions.md` + `docs/memory/index.md`，靠 SessionStart hook
读索引带进上下文。这套在 Qoder 下**完全失效**：hook 不触发，`docs/` 下的文件没有任何
机制保证会被读到。

原 SKILL.md 自己写明了硬约束：「IDE 聊天记录会被清除，且 Hook 无法感知对话内容」。
Qoder 的长期记忆直接解决这件事 —— 自动召回、跨会话、跨项目。

## 落点对照

| 内容 | 落点 |
|---|---|
| 需求业务口径（聚合/边界/降级、做不做、待确认项） | ❌ 不落记忆 → **XMind 节点标注 + 需求分析文档 + 台账**（记确认日期与确认人） |
| 踩坑、根因、修复方式（工具/脚本/链路行为） | `common_pitfalls_experience` **并同步进 `.qoder/rules/known-pitfalls.md`**（团队共享） |
| 我的理解被用户纠正（工程行为类） | `common_pitfalls_experience` |
| 项目环境 / 目录结构 / 配置位置 | `project_environment_configuration`；团队要用的进 AGENTS.md / rules |
| 用户的工作方式约束（如「多动作要给选择框」） | `user_behavior` |
| 一个需求收口后的整体结论 | `task_summary_experience`（个人缓存；**团队真相在台账**） |

`docs/lessons-learned.md` **保留**，但降级为「给人翻的历史台账」，不再是唯一落点。
只写它 = 等于没记。

## 必须记（记忆）

- **跨需求可复用的工程经验**：执行跑不通后的降级处理、工具 partial_success/静默失败模式、
  环境与脚本的坑 —— 记完同步进 `known-pitfalls.md`
- 我的理解**被用户纠正过**（工程行为类）—— 写清错在哪、正确是什么
- 用户明确要求记住的工作方式约束

## 必须落台账 / 文档（不是记忆）

- 需求方**口述澄清**的业务口径 —— 落 XMind 标注 + 台账，记确认日期与原话
- 已登记但**未闭环**的待确认问题、产品风险 / 缺陷线索 —— 落台账「仍悬挂」栏
- **已判定不考虑**的项 —— 落台账（负信息不留痕的话，下次会被重新报成缺口）

## 不要记

- **单需求的业务口径**（见一票判据第 2 条 —— 落 XMind + 台账，不落记忆）
- 需求文档里已写清楚的内容（写来源引用即可，别复制原文）
- 一次性的调试过程、闲聊、探索性提问
- 已经记过的同一条（**先 `SearchMemory` 查，有就 update，不要新建重复条目**）
- 凭据、密码、token —— **任何情况都不记**，包括用户主动要求时

## 写入时机

1. **用户说触发词**（记一下 / 存档 / 记住这个 / 沉淀一下）→ 立即写入并告知落在哪
2. **我的理解被纠正的当场** → 立即写，不等会话结束
3. **一个需求收口时** → 口径整理进台账与 XMind 标注；只有反映**工具或链路行为**的经验才落记忆

注意：**没有 hook 会提醒记忆写入**（现有 3 个 hook 管的是格式拦截与失败处置，不管这件事）。
所以写入完全靠当场自觉，没有兜底机制。

## 复用纪律（记忆的价值全在这一步）

新需求启动时先 `SearchMemory` 查有无同类，并读该需求台账。命中之后：

- **已确认的口径不要再问用户一遍**（口径查台账，不查记忆）
- 引用时**标注确认日期**，并提示用户确认是否仍然有效 —— 业务口径会变，不能当永久事实用
- 与当前代码 / 配置冲突时，**以当前代码为准**，并回头修正那条记忆
- 存量的业务口径记忆（`important_decision_experience`）在对应需求收口时迁入台账后**删除**，不再新增此类记忆

## 禁止

- ❌ 把记忆当对话逐字稿，大段复制原文
- ❌ 同一条口径记成多条（先查再写）
- ❌ 直接拿记忆里的口径当事实用，却不告知来源和日期
- ❌ 每次会话都记一条，把记忆淹在噪声里
