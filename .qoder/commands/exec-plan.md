# 测试执行计划

承接已评审通过的用例，产出可落地的执行方案。

> 这原本是 `.trae/agents/execution/agent.md`。**没有做成 subagent**，因为制定执行计划
> 需要反复和你确认测试环境、数据权限、可用工具 —— subagent 跑起来就无法对话了。

## 输入

- 评审通过的用例（`docs/test-cases/` 下的 `.xmind`）
  用 `python3 scripts/parse_xmind.py <file> --output /tmp/cases.txt` 解析
- 测试环境信息（**要问用户**：哪套环境、有无数据库/MQ 权限）
- 已有的测试数据情况

## 先问清楚再动手

用 `AskUserQuestion` 确认这几件事，别自己假设：

- 目标环境（测试 / 预发 / 灰度）
- 有没有并发压测、MQ 消息构造这类需要工具支持的场景
- 执行是一个人还是多人分工

## 输出

- 执行计划：`docs/reports/<需求名>_execution-plan.md`
- 执行报告：`docs/reports/<需求名>_execution-report.md`（执行完成后）

## 执行计划要包含

1. **执行顺序** —— 按用例优先级排（P0 正向/生命周期/并发 先跑）
2. **测试数据准备清单** —— 每条数据说明：谁准备、怎么造、依赖哪个后台配置
3. **需要工具支持的场景** —— 并发测试、MQ 构造、定时任务触发，逐项说明手段
4. **阻塞项** —— 缺权限、缺配置、依赖上游未上线的，单独列出并标注影响范围
5. **时间估算** —— 按模块给区间，不给单点数字

## 执行报告要包含

1. 用例执行结果统计（通过 / 失败 / 阻塞 / 未执行）
2. 缺陷清单（含严重级别和对应用例编号）
3. 未覆盖到的场景及原因
4. 剩余风险

## 约束

- **阻塞项要显式列出**，不要含糊写「视情况而定」
- 数据准备清单要具体到可执行，不要写「准备测试商品」这种没法照做的
- 发现用例本身有问题（步骤不可执行、预期无法判断），回到评审环节，不要在执行阶段偷偷改用例
