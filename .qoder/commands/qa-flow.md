# 启动 QA 事务式工作流

按 `qa-workflow` skill 定义的流程执行。**方法论细节一律以该 skill 为准，不要在这里另立一套。**

## Step 0：台账定位（先于一切）

1. 问清需求名后，查 `docs/requirements/<需求名>_台账.md`：
   - **不存在** → 按 `docs/requirements/_台账模板.md` 创建，填元信息
   - **已存在** → 通读全文，这是**断点续跑的依据**：
     - 「阶段进度」表里已 ✅ 的 Step **不重跑**，从第一个未完成的 Step 继续
     - 「已确认口径」里的问题**不要再问用户一遍**；「已判定不考虑」的项不要重新报成缺口
2. 建 todo 列表（5 条：Step 1 / 1.5 / 2 / 3 / 4），已完成的直接标 COMPLETE
3. 用 `AskUserQuestion` 确认输入：需求来源（Confluence / 飞书 / 直接贴文本）、有没有历史用例可参考

## 铁律：每步必须停，停完必须写台账

每个 Step 结束用 `AskUserQuestion` 推送选项（通过 / 需要调整 / 打回上一步 / 暂停），
**用户确认前禁止进入下一步**。

用户确认「通过」后、进入下一步前，**立即写台账**：
- 「阶段进度」该行更新为 ✅ + 产出物路径 + 日期
- 本步确认的口径 → 追加进「已确认口径」（带日期、确认人）
- 用户明确说不管的 → 追加进「已判定不考虑」
- 新冒出来的未闭环问题 → 追加进「仍悬挂」

对话中需求方**口述澄清**的口径，**当场**追加台账，不等步骤结束——台账是唯一状态载体，不落记忆。

## Step 1.5 是硬 gate，不能跳

用 ≤8 行把核心判定链路讲清楚，每一环标注数据来源。**不落文件，纯对话确认。**
链路被纠正后要**重新输出完整链路再确认**，不要直接跳去展开场景。
确认后在台账「阶段进度」记一行结论日期即可。

## Step 4 评审门禁（打回循环）

1. 派 `case-reviewer`（派发契约见 `delegation-discipline.md`：必须给它用例文件路径 + 需求分析路径 + 台账路径）
2. 回传后，把「高优先级发现条数 + 最关键 3 条 + 是否建议打回」呈给用户，
   用 `AskUserQuestion` 推送：**通过定稿 / 按评审意见修改后重评 / 部分采纳（用户指定哪几条）**
3. 选「修改后重评」→ 按评审发现重新生成 XMind（重生成前提醒用户关闭 XMind 客户端）→ **重新派 case-reviewer**，
   循环直到用户选「通过定稿」；每轮打回在台账「阶段进度」记打回轮次
4. **未走完这个门禁的用例禁止标记为最终版**

## 派 subagent 的时机

| Step | 何时派 | 派给谁 |
|---|---|---|
| Step 1 | 需求材料在 Confluence / 飞书，量大需要通读 | `requirements-analyst` |
| Step 4 | 用例已成型，要通读全文 + 对照需求做评审 | `case-reviewer` |

**subagent 不能和用户对话。** 所以：
- Step 1 派出去只是拿「材料 + 分析初稿 + 待澄清问题清单」，
  **回传后由主会话带用户逐条对齐** —— 对齐这件事不能外包
- 材料少（用户直接贴了需求文本）就不用派，主会话直接做更快
- 派发与回传处理的完整纪律见 `.qoder/rules/delegation-discipline.md`

## 落盘时机

对齐阶段（Step 1 讨论、Step 1.5 链路、Step 2 清单讨论）**全部在对话里进行，不落中间态 md**。
理解还在偏差期就写文件，必然返工。只在该 Step 结论稳定、用户确认后落盘一次——**台账追加除外**（口径当场记）。

## 输出格式

全部产出物的格式与落位以 `output-schema.md` 矩阵为准：
Step 3 用例**默认 XMind**（直构 JSON + `scripts/gen_xmind.py`）；评审报告（Step 4）是给人读的，用 MD 是对的。
