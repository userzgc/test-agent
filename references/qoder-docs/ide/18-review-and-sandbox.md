# Ultra Review、Quest 审查与提交、终端与沙箱（Qoder IDE）

> 来源：/zh/user-guide/chat/ultra-review + /zh/user-guide/quest/review-and-commit + /zh/user-guide/quest/terminal-and-sandbox

## Ultra Review 智能体

把审查**拆成多个独立维度并行执行**，再合并去重，输出信噪比更高、定位更精确的结构化报告。

### 三视角并行

| 维度 | 盯什么 |
|---|---|
| **Completeness（需求完整度）** | 变更是否真正落地需求意图？**验收点、API 契约、状态分支**是否都覆盖，有没有只实现一半的逻辑 |
| **Correctness（编码正确性）** | 逻辑漏洞、空指针与越界、错误处理与边界条件、并发与资源泄漏、明显的安全或性能风险 |
| **Impact（变更影响面）** | 副作用（全局状态、IO、并发、生命周期 hooks）+ 对既有契约的破坏（API、默认值、schema、配置向后兼容） |

三维度发现经统一合并去重 —— 命中同一处代码的问题归并为一条，**保留证据最充分的那份**。

### 核心能力

- **严格的发现门槛**：每条发现需同时满足「**问题确定（非推测）、由本次变更引入、有可引用的证据**」
- **精确定位**：锚定具体文件与行号，附证据片段与可执行修复建议
- **严重度分级**：**Critical**（必须修复）/ **Warning**（建议修复）/ **Suggestion**（可考虑）
- **单点容错**：某维度无产出时其他维度仍正常返回，并在报告中标注缺失项

### 审查范围（`/ultra-review`）

1. 优先审查**未提交变更**（staged + unstaged）
2. 没有未提交变更 → 自动回退到**最近一次 commit**
3. 也可显式指定：commit hash、文件路径、**Pull Request** 或一段代码片段

> ⚠️ **Ultra Review 目前在 Quest 视窗的智能体模式下不可用。**

### 最佳实践

- 大型变更**按模块或按提交分批审查**
- 涉及特定业务背景或非显性约束时，**在请求里简要说明上下文**

> 🎯 对本项目：这套「三维度 + 严格证据门槛 + 分级」的结构，
> 正是 `.trae/agents/` 里那个「用例评审 Agent」想做的事。
> 用例评审可以照搬这个骨架：**完整性（需求覆盖）/ 正确性（步骤与预期）/ 影响面（与既有用例冲突或重复）**。

## Quest 审查与提交（Review 面板）

三个区域：**顶部操作栏**（范围切换、Stage All / Discard All、提交按钮）、
**文件列表**（列表/文件树视图切换 + 搜索）、**Diff 视图**（行级对比 + 单文件 Stage/Discard）。

### 查看范围

| 选项 | 含义 |
|---|---|
| **Current Quest** | 当前 Quest 累计的全部变更 |
| **Last Turn** | 最近一轮对话产生的变更 |
| **All Uncommitted** | 工作区所有未提交变更（`git status` 中所有有改动未 commit 的文件） |

### ⭐ 在代码与 Diff 中批注

可针对具体内容添加批注，**把反馈直接交给智能体**，
无需另外用文字描述「哪一处、要怎么改」。

### 暂存与丢弃

- `Stage All` / `Discard All`（后者**需二次确认，无法恢复**）
- 单文件：未暂存显示 `Stage`+`Discard`，已暂存显示 `Unstage`+`Discard`
- ⚠️ **Hunk 级（文件内局部变更）暂不支持单独 Stage/Discard**
- Stage/Unstage 需当前目录为 Git 仓库
- ⚠️ **外部改动提示**：Current Quest / Last Turn 范围下，若文件在本次对话之外还有其他改动，文件名旁显示黄色 ⚠️

### 提交与推送

Commit 入口在所有维度下均可用 —— 从 All Uncommitted 提交整个工作区，
或从 Current Quest / Last Turn **只提交当前范围内涉及的文件**。

顶部按钮默认 **Commit**，下拉可切换 **Push** / **Create New Branch**（基于当前变更创建新分支并提交）。
Commit 弹窗可手动控制是否包含未暂存变更；message 可手填或自动生成。

## 终端与沙箱

分层安全模型：按运行模式和命令风险等级，自动决定**直接执行 / 沙箱隔离执行 / 暂停等确认**。

### 执行模式对比

| | Agent 模式 | Experts 模式 |
|---|---|---|
| **常规命令** | 不在内置风险类别中的直接自动运行（`npm install`、`git status`、`python test.py`） | 所有不在内置风险类别中的直接执行，**不检查用户自定义黑名单** |
| **风险命令** | 命中风险类别或**你配置的黑名单** → **暂停等你批准或拒绝** | **自动在沙箱中执行，无需确认** |
| **权限升级** | — | 沙箱中失败或模型判断必然失败 → AI 分析原因并可能**请求升级权限**，此时暂停询问 |

**潜在危险命令**：文件删除、磁盘操作、权限管理、网络配置等类别。
此外 **AI 模型会根据命令语义独立判断风险**，即使命令不在上述类别中。

### 沙箱平台要求

| 平台 | 实现 |
|---|---|
| **macOS** | 开箱即用，基于系统自带 **Seatbelt** 框架实现内核级隔离 |
| **Windows** | 自研沙箱引擎随 IDE 分发，支持 Win7+，**无需 WSL** |
| **Linux** | 需安装 **bubblewrap（`bwrap`）**。首次使用时会弹窗引导一键安装（自动识别 apt/dnf/yum/pacman/zypper）。不安装则**降级为非沙箱执行**并提示 |

### 沙箱工作方式

**文件系统**：工作区目录可写，其余目录**只读**；`~/.ssh` 等敏感路径对沙箱内进程**不可见**。

### 升级流程

沙箱失败 → AI 分析是否为沙箱限制导致 → 请求升级 → IDE 暂停询问 → 批准后在终端直接执行（无沙箱限制）。
也可取消该命令让 Agent 尝试其他操作。

### ⚠️ 注意事项

- **域名级网络过滤尚未支持**：目前网络控制是粗粒度开/关模式
- **Linux 容器环境**：Docker 内使用时隔离能力受限，目前仅做文件系统和网络隔离
- **Windows 沙箱为用户态机制**：防误伤性写入和意外外联，**不能完全覆盖对抗性攻击**
- ⭐ **Shell 主题兼容性**：Powerlevel9k/Powerlevel10k 等主题可能**干扰终端输出**导致截断或格式错乱。
  出现这种情况时在 Agent 运行时禁用该主题或切到更简洁的提示符

> 🎯 最后一条对本项目直接相关：用户 shell 是 `/bin/zsh`，
> 如果装了 Powerlevel10k，脚本类 hook 的输出可能被污染 —— 这是一个隐蔽的 hook 失效原因。
