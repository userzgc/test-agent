# Better Harness（Qoder IDE）

> 来源：https://docs.qoder.com/zh/user-guide/knowledge-engine/better-harness
> 触发：左侧栏底部 **Better Harness**（与「知识中心」「插件市场」并列），或运行 `/better-harness`
> ⭐ **这个 Skill 在本会话中就是可用的**——是当前 6 个可用 skill 之一。

## 为什么它对本项目直接相关

官方对问题的描述几乎是本项目现状的逐字复述：

> 「本该写下来的规则只留在某个人的脑子里、**复盘发现的问题没有沉淀成规则**、
> 团队约定散落在群聊里、**`AGENTS.md` 里空空如也**。」

本项目正是：踩坑记录写在 `docs/lessons-learned.md`（无机制保证被读）、
6 篇 steering 规则写在没人读的目录、根目录**没有 `AGENTS.md`**。

## Agent Harness 是什么

Agent Loop = 「理解任务 → 执行操作 → 查看结果 → 继续调整」的循环。

> 「真正可靠的 Loop，不只是让 Agent 一直行动，而是让它知道**目标是什么**、
> **哪些地方不能动**、**怎么判断结果对不对**，以及**失败后该怎么办**。
> 否则它可能改了很多代码、跑了很多测试，最后却无法证明任务真的完成了。」

在 Qoder IDE 中，Loop 工程涵盖的资产类型：
**Rules、Skills、Hooks、MCP 配置、Custom Agents、Plugins、Session Insights**。

## 工作方式

分析过程四步：

1. **画出当前 Harness** — 识别目标、上下文、执行入口、反馈、交付和学习机制
2. **找到断点** — 说明哪一环缺少机制、接入、实际执行或结果证据
3. **选择最小改进载体** — 把问题交给最合适的 Rule / Skill / Hook / 脚本 / 自动化 / 人工门禁
4. **修复并复验** — 限定修复范围，执行相关验证，**再次运行 `/better-harness` 检查 Loop 是否真的改善**

分析时主流程先收集原始数据，再交给**三个相互独立的只读子 Agent** 分别解读三类证据：

| 证据类 | 内容 |
|---|---|
| **Agent 自定义资产** | Rules、Skills、Hooks 等配置是否完整可用 |
| **真实的任务会话记录** | Agent 在实际任务中做了什么、结果如何 |
| **项目的软件工程基础** | — |

三类证据独立收集再统一汇总，**避免结论互相污染**。

## 五个评估维度

| 维度 | 检查什么 |
|---|---|
| **任务理解** | Agent 能否识别项目是什么、任务从哪开始、改动范围控制在多大 |
| **可控执行** | 能否按项目说明启动项目、在明确权限内完成任务、守住操作边界 |
| **改动验证** | 每次改动是否经过 lint、测试等检查；**失败后是否能修复再验证** |
| **可靠交付** | 结果是否有**可核验的证据**支撑验收；高风险操作是否有审批/回滚/恢复方案 |
| **经验沉淀** | 反复出现的问题是否已沉淀为**可查找、可复用**的规则或 Skill，**并在后续同类任务中被真正用上** |

每个维度以条形图展示分数 + 标注相关优化点数量。
报告同时展示项目当前 **Scope 概览**：Rules、Skills、Custom Agents、MCPs、Memories、Hooks。

> ⭐ 「经验沉淀」维度的判据是**"被真正用上"**，不是"写下来了"。
> 这正好解释了为什么本项目 6 规则 / 9 skill / 6 agent 全写在 `.trae/` 却等于零分。

## 使用流程

1. 左侧栏底部点 **Better Harness**
2. 顶部 tab 切换项目，**+ 添加项目**
3. 首次扫描会显示「正在理解项目结构…」——Agent 读取模块结构、**历史会话**、已有 Skills；
   扫描期间可在 **Quest 列表**看进度
4. 报告生成后概览页展示五维分数 + 优化点数量 + Scope 统计
5. 下方列出优化点卡片，可按 **全部优化点 / 已处理 / 待处理** 筛选；
   每卡标注**优先级（高/中/低）**、标题、所属维度
6. 卡片上点 **创建修复方案** 启动修复；不需要的点 **忽略**
7. **重新生成** 发起新一轮扫描；**查看详情** 进入完整报告页

> **Better Harness 不会自动修改代码。** 所有修复都以 Quest 任务形式呈现，
> 可审阅、可回滚——它只负责指出问题并准备好提示词。

## 创建修复方案

点 **创建修复方案** 弹出 **问题详情** 对话框：

- **优先级** 标记（高/中/低）
- **问题标题** 与所属维度（如「修复计划 · 任务理解」）
- **原因** — 为什么当前配置存在该短板
- **预期输出** — 修复完成后的预期结果
- **修复说明** — 一段**可编辑的提示词**，默认以 `/harness` 开头并预填修复方案

底部有模型选择器和 **开始修复**。点击后用修复说明**创建一个新的 Quest**。

> 「这些修复不仅服务于当前任务，还可以进一步**沉淀为 Rules、Skills、Memories 等可复用的用户资产**。」

## 完整报告页（查看详情）

| 模块 | 内容 |
|---|---|
| **Agent 工作流** | 五个维度分数节点的流水线可视化 |
| **项目用量** | 每日活动热力图、已分析会话数、估算活跃分钟数、**Skill 使用次数**、最常使用的 Skills |
| **优先优化项** | 全部优化点卡片，可 **规划 AI 修复** 或 **查看详情** |
| **Agent 自定义** | 已发现的 Loop 工程资产（Hooks、MCP、Plugins）及覆盖范围（Rules、Skills、Session Insights、Custom Agents 是否已配置） |
| **证据与方法** | 抽样可信度、来源缺口、交付结果概况，说明结论依据的数据量 |
| **长会话待复核** | 标记出**超过 45 分钟**的会话供人工检查 |
| **会话观察** | 从已分析会话中提炼的代表性观察条目 |

> **「Skill 使用次数」这个指标可以直接验证 skill 是否真的在被调用**——
> 本项目迁移完 9 个 skill 后，用它来验证迁移是否有效。

## 建议重新生成的时机

- 按报告修复了一批 Loop 工程问题，想看分数变化
- 项目结构发生较大变化（新增模块、大范围重构）
- 距上次报告超过两三周

报告卡片显示更新时间（24 小时制、当地时区），新报告**替换**原有报告。

## 🎯 本项目的下一步动作（直接可执行）

在动手迁移 `.trae/` 之前，先跑一次 `/better-harness` 拿基线分数：
它会自己扫出「Rules 未配置、Skills 未配置、Custom Agents 未配置、Hooks 未配置」，
输出的优化点清单和优先级**可以直接当作迁移工单**，而且修复走 Quest 可审可回。
迁移完再跑一次对比分数，这就是官方设计的闭环验证方式。
