# Quest —— 任务委派工作台（Qoder IDE）

> 来源：/zh/user-guide/quest/overview + agent-mode + experts-mode + goal-driven + spec-driven

Quest 是独立视窗的 Agent-first 工作台。**核心理念：Define the goal. Review the result.**
聚合 **Agent** 与 **Experts** 两种子模式。

⚠️ **模式在任务创建时确定，后续不能切换。** 编辑消息会触发**工作区文件回滚**到本次会话之前的状态。

## 三栏布局

| 区域 | 内容 |
|---|---|
| **左侧 · 任务管理区** | 以**工作区**为组织单位（可加多个文件夹）。Quest 支持 Pin / Fork / 重命名 / 删除。状态：`Running` / `Action Required` / `Ready` / `Error`。轻量提问可不绑定项目 |
| **左侧底部 · 拓展功能** | **知识中心**（Repo Wiki + 知识卡片 + Memory）、**插件市场**、**设置** |
| **中间 · 会话区** | 会话流、执行步骤、输入框（`@` 引用 / 模型选择 / 语音 / 上下文压缩）、变更概览入口、侧边快速定位 |
| **右侧 · 功能区** | **概要**（Progress + 概要文件 + **引用**）、**审查与提交**、终端与文件树、浏览器、Spec 面板、Supabase 面板 |

> ⭐ 功能区「**引用**」模块展示当前任务**所用的知识和工具（Repo Wiki、Memory、Skills、MCP）**，支持点击跳转。
> 这是验证「我的 Skill / Rule 到底有没有被用上」的**直接观测点**——比猜测可靠得多。

**My Quests 全局看板**：跨工作区汇总，搜索栏 + 工作区筛选 + 三列看板（Running 蓝 / Waiting 橙 / Completed 绿）。

**平铺布局**：拖拽 Quest 到不同窗格并行处理，布局设置跨会话保留。

## 四种执行范式对比

| | 触发 | 定位 | 输入 | 执行方式 |
|---|---|---|---|---|
| **Agent 模式** | 模式切换 | 智能体自主端到端交付 | 自然语言任务 | 单 Agent 执行 |
| **Experts 模式** | 模式切换 | 多智能体并行协同 | 自然语言需求 | Lead Agent 调度多专家 |
| **Goal 驱动** | `+` → Goal 开关，或 `/goal` | 目标导向，Agent 自主规划路径 | **描述期望的最终状态** | 自驱迭代，自行判断完成度 |
| **Spec 驱动** | `+` → Spec 开关 | 规划为蓝图，按方案逐项实现 | 结构化方案描述 | 按 Spec 任务清单顺序执行 |

Goal 与 Spec **可叠加**：生成 Spec 后打开 Spec 卡片上的「目标」开关再执行，即以 Goal 模式围绕该 Spec 自主迭代。

## Spec 驱动流程（⭐ 与本项目最贴合）

1. **需求澄清** —— Quest 以**选择题形式**提澄清问题
   - `Recommend` 自动选默认答案 / `Continue` 手动选后继续 / `Skip` 跳过直接对话
2. **生成 Spec** —— 结构化文档含 **需求描述 / 设计方案 / 任务拆分 / 验收标准**，右侧 Spec 面板流式输出，**支持下载**
3. **审核 Spec** —— 可对话修改；也可**在 Spec 文档中针对具体内容加批注**，反馈直接交给智能体（不用把意见整理成一段话）
4. **执行与监控** —— 进展实时显示、变更文件在概要文件区、**随时追加需求，Quest 会调整计划**
5. **审查与提交** —— Diff 审查 → 暂存/丢弃 → 提交 / 推送 / **基于变更创建分支**

**从 Spec 转定时任务**：生成 Spec 后不点执行，改点「**设置定时**」，Quest 在计划时间自动执行（适合夜间错峰）。

> ⭐ 「需求澄清 → 结构化 Spec（含验收标准）→ 人工审核 → 执行 → 审查」这条链
> **正是本项目 `.trae/agents/` 手工搭的那套多 Agent 编排想做的事**，而 Quest 是框架原生实现。
> 本项目「需求分析 → 用例编写 → 用例评审 → 执行」的流程，用 Spec 驱动 + 自定义专家可以直接映射。

## Goal 驱动细节

- 目标应描述**期望结果**而非具体步骤：`/goal 将项目测试覆盖率提升至 80%`
- 每轮执行后自动评估进度，未达成继续迭代
- ⚠️ **默认最多推进 10 回合**，达上限自动结束。
  可在 **设置 → 集成 → 内置能力 → 目标驱动执行** 调整最大回合上限
- Goal 进度卡片支持：**编辑**（运行中编辑在当前轮次结束后生效；暂停中编辑立即生效）、
  **暂停与继续**（保留完整上下文与中间产物）、**删除**（已生成文件和消息不删除）
- 最佳实践：描述可验证的最终状态 / 加入关键约束 / 适当缩小范围 / 结合 `/schedule` 定时执行

## Experts 模式的 7 个角色

| 角色 | 职责 |
|---|---|
| **Lead Agent** | 理解需求、拆解任务、协调调度、质量把关 |
| 调研员 | 调研分析、代码定位、依赖梳理、环境检查与报告输出 |
| 全栈工程师 | 前后端代码实现修改、跨栈或通用编码任务 |
| **QA** | 运行测试构建流程，收集整理**验证结果与相关证据** |
| 代码审查员 | 代码审查、风险识别与检测、改进建议 |
| UI 操作者 | 浏览器与 UI 端到端验证、可视化 Bug 复现 |
| 故障诊断工程师 | 故障复现、根因定位、缺陷诊断与修复建议 |

专家之间**互不阻塞、并行执行**，Lead Agent 实时对齐整合结果。

**内置专家可自定义**（⚠️ **Lead Agent 不支持自定义**）：
- **模型选择** —— 可为单个专家指定特定模型，精细控制成本/能力权衡
- **追加提示词** —— 最多 **10,000 字符**，引导或约束特定场景行为
- **Skills 与 MCP** —— 为内置专家扩展能力边界

**自定义子智能体**同时适用于 Agent 与 Experts 模式，由主智能体按需自主调用。

**需要人工介入的极少数情况**：终端命令命中黑名单或被识别为高风险 / 工具调用次数达上限 / 其他异常。
⚠️ **Experts 模式下终端命令自动运行无需每次确认，潜在危险命令自动在沙箱中运行。**

**专家团全景图（Expert Team Canvas）**：点任务进展卡片上的专家头像打开。任务总览面板 + 卡片式画布视图。

官方数据：相比单 Agent 耗时增加，但**内部测试显示质量提升约 67%**。简单明确的文件修改用 Agent 模式更高效。

## 🎯 对本项目的映射建议

| 本项目现有环节 | Quest 对应载体 |
|---|---|
| 需求分析 Agent | Spec 驱动的「需求澄清 + 需求描述」阶段 |
| 用例编写 Agent | 自定义子智能体 + Skill，或 Experts 的 QA 专家（加追加提示词） |
| 用例评审 Agent | 代码审查员角色的类比 / 或 `agent` 类型 Hook 做硬校验 |
| 手写 `multi-agent-orchestration.md` 路由表 | **Lead Agent 原生调度**，路由表可以删 |
| 「每次都要人工确认产出物」 | 审查与提交面板 + Spec 批注 |
| 长耗时批量生成用例 | Goal 模式 + `/schedule` 夜间执行 |
